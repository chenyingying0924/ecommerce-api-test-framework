# 缺陷记录（Bug 记录文档）

> 诚实性说明：本项目是个人练习项目，没有真实生产环境，因此**没有"真实生产缺陷"**。
> 缺陷来源只有两类，都会如实标注：
> 1. **故障注入实验**：故意往代码里植入 bug，验证测试用例能否抓住它；
> 2. **已知行为 / 设计限制**：不是 bug，但值得记录和讨论（如幂等缺失）。
> 绝不编造"在生产环境发现严重 bug"的经历。

## BUG-001【故障注入实验】下单接口未提交事务，订单"假成功"

- **缺陷编号**：BUG-001
- **缺陷标题**：POST /orders 返回 201 但订单未写入数据库（未执行事务提交）
- **前置条件**：服务以独立测试库启动（`SHOP_DB_PATH=test_shop.db`），自动化测试套件可运行
- **复现步骤**：
  1. 打开 `app/main.py`，找到 `create_order` 函数
  2. 在 `conn.commit()` 行首加 `#` 注释掉它，保存（`--reload` 会自动重启服务）
  3. 运行 `SHOP_DB_PATH=test_shop.db pytest tests/ -v`
- **预期结果**（注入前基线）：10 passed
- **实际结果**（2026-10-18 实测）：**3 failed, 7 passed**
  - `test_order_is_persisted_in_database` — AssertionError: 订单 8 应在 orders 表中有且仅有 1 条，实际 0 条
  - `test_stock_is_updated_in_database` — AssertionError: 下单 3 个后，数据库里键盘库存应为 50-3=47（实际 50）
  - `test_create_order_deducts_stock_and_matches_total` — AssertionError: 库存应减少 2，实际 50 -> 50
  - 注：HTTP 层断言（201、total_price=398）全部依然通过——"接口说谎"成立
- **严重程度**：严重（订单数据丢失，但接口返回成功，用户和商家都以为下单成功了）
- **优先级**：P0
- **环境信息**：macOS 26.2 / Python 3.12.6 / FastAPI + uvicorn(:8000) / SQLite(test_shop.db)
- **根因分析**：SQLite 的写操作在事务里执行，`commit()` 之前数据对其他连接不可见；连接关闭时未提交的事务被**回滚**。于是接口把 201 返回给了调用方，数据库却恢复原样——典型的"接口说谎"。
- **修复方法**：恢复 `conn.commit()`
- **修复验证结果**：恢复 `conn.commit()` 后重跑 `pytest tests/ -v` → **10 passed in 0.08s**
- **来源**：**故障注入实验**（人为植入，非真实发现）
- **执行复盘**：预测 2 条失败，实际 3 条——API 相对断言（GET /products 读库存差值）同样感知到了回滚。三条失败用例的诊断能力有层次：DB 断言直接指出"订单未落库"（离根因最近，实际 0 条），另两条只显示"库存未变"（需再排查一步）。**抓到 bug 是及格，定位根因是优秀。**

### 这个实验证明了什么（面试可讲）

- 只断言 HTTP 状态码/响应字段的断言（201、`total_price == 398`）**全部依然通过**——因为接口确实返回了正确的 201 和金额；
- **数据库断言**用例（订单落库、库存落库）全部失败，且失败信息直接指向根因（"订单 8 实际 0 条"）；
- 连 API 层的库存相对断言也失败了（50 -> 50）——但它只能告诉你"库存没变"，定位根因还需多查一步；
- 结论：接口测试必须配合数据校验，才能覆盖"接口说谎"这类缺陷。这就是阶段 6 那两条 DB 用例的价值证明。

## KNOWN-001【已知行为】下单接口不具备幂等性

- **描述**：完全相同的下单请求连续发送，会生成多张订单、多次扣库存（TC-ORDER-010 实测：两次请求 → order_id 6、7，库存扣 2 次）。
- **是否缺陷**：取决于业务需求。若需求要求"防网络重试导致重复下单"，则应做幂等（如客户端生成唯一请求号）；本项目未实现，作为已知限制记录，且在简历/面试中如实说明。
- **严重程度 / 优先级**：视业务而定（电商场景通常 P1）
- **来源**：已知行为

## KNOWN-002【已知限制】登录 token 未被强制校验

- **描述**：`/login` 返回 token，但所有接口均不校验它（业务规则说明.md 已标注）。
- **影响**：任何人拿到 user_id 即可代替他人下单（越权风险）。真实系统必须修复。
- **来源**：已知限制（阶段 1 明确标注未实现）
