# 被测系统业务规则说明（阶段 1 第一版）

> 本文档描述当前**已实现**的规则。未实现的功能在文末明确列出，不冒充已完成。

## 1. 用户注册（POST /register）

- `username`：3~20 个字符，全系统唯一。重复注册返回 **409**。
- `password`：6~30 个字符。不满足时 FastAPI 自动返回 **422**。
- 密码只保存哈希值（sha256），不保存明文。
- 成功返回 **201** 和新用户 `id`。

## 2. 用户登录（POST /login）

- 用户名或密码错误 → **401**（两种错误返回同一提示，不泄露用户名是否存在）。
- 成功返回 **200** 和一个随机 `token`。

## 3. 商品（GET /products、GET /products/{id}）

- 演示商品：机械键盘 ¥199/库存50、无线鼠标 ¥89/库存100、显示器 ¥899/库存20。
- 查询不存在的商品 id → **404**。

## 4. 创建订单（POST /orders）

一次下单按顺序执行以下校验，任何一步失败都不会产生订单：

1. 用户必须存在，否则 **404**。
2. 商品必须存在，否则 **404**。
3. 数量必须大于 0（请求体校验，否则 **422**）。
4. 数量不能超过当前库存，否则 **409**（库存不足）。
5. 校验全部通过后：写入订单（状态 `created`，金额 = 单价 × 数量），**同时**把商品库存扣减相应数量。两步在同一个事务里提交。

**核心业务规则：订单创建成功 ⟺ 库存精确减少对应数量。** 这条规则是后面数据库校验（阶段 6）的重点测试对象。

## 5. 购物车（阶段 1 第二批新增）

- **加入购物车** `POST /cart/items`：用户和商品必须存在（否则 404）；数量必须大于 0（否则 422）。同一商品重复添加时**数量累加**：第一次返回 **201**，之后合并进已有条目返回 **200**（响应里有 `merged` 字段区分）。加购物车**不校验、不占用库存**——购物车只是"想买"，结算时才真正扣库存。
- **查看购物车** `GET /cart/{user_id}`：返回每个商品的名称、单价、数量、小计和购物车总金额（通过 JOIN 关联商品表）。购物车为空时 `items` 是空数组 `[]`。
- **修改数量** `PATCH /cart/items`：把某商品数量**直接改成**新值（不是累加）；购物车中没有该商品 → 404。
- **删除条目** `DELETE /cart/{user_id}/items/{product_id}`：成功 200；不存在 404。
- **结算** `POST /cart/checkout`（核心规则，重点测试对象）：
  1. 购物车为空 → **409**；
  2. 先整体校验所有商品的库存，**任何一件不足 → 409，且整单不生效**（回滚：不产生订单、不扣库存、不清购物车）；
  3. 全部通过后：每个商品各生成一张订单（状态 `created`）→ 逐个扣库存 → **清空购物车**，三件事在同一个事务里一起生效。
  4. 结算成功后再次结算 → 409（购物车已被清空）。

## 6. 当前未实现的功能（后续阶段再做，勿在简历/讲述中冒充已完成）

- 订单状态流转（创建 → 支付 → 取消）
- 登录 token 的强制鉴权（现在所有接口都可以不带 token 调用）
- 取消订单并回补库存
