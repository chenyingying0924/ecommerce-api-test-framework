## 二、设计方法速查（结合订单模块）

### 1. 等价类划分
把"海量可能的输入"划分成几类，每类抽一个代表值来测，避免穷举。

- 数量 quantity：合法(1~库存)、非法(≤0)、超库存(>库存)、非法类型(非整数)。
- 商品 product_id：存在、不存在、非法类型。
- 用户 user_id：存在、不存在。

### 2. 边界值分析
bug 最常藏在"分界线"上，所以要专门测边界。边界值三件套：**刚好等于、刚好差一点、刚好多一点**。

- 数量下边界：0（应拒绝）、1（最小合法值）。
- 数量上边界：库存值（刚好够，应成功）、库存+1（刚好不够，应拒绝）。

### 3. 状态迁移
关注"操作前后系统状态怎么变"，并验证变化后的行为。

- 订单创建成功 → 订单状态 = created，商品库存减少。
- 库存扣到 0 后，再下单 → 应 409（状态变化导致后续行为改变）。

## 三、示范用例（TC-ORDER-001 ~ 003，已执行）

### TC-ORDER-001 正常下单
- 测试模块：订单创建
- 测试目的：验证正常下单流程能成功创建订单并正确扣库存
- 前置条件：用户 id=1 存在；商品 id=1（机械键盘）库存 ≥1
- 测试数据：user_id=1, product_id=1, quantity=1
- 操作步骤：调用 POST /orders，body = `{"user_id":1,"product_id":1,"quantity":1}`
- 预期结果：状态码 201；返回 order_id 且 status="created"；total_price = 199.0；商品1库存减少1
- 实际结果：201；order_id=4；product_name=机械键盘；total_price=199.0；status=created
- 执行状态：通过

### TC-ORDER-002 数量 = 当前库存（上边界·合法）
- 测试模块：订单创建
- 测试目的：验证数量刚好等于库存时能成功下单（上边界值）
- 前置条件：用户 id=1；商品 id=1 当前库存 = N（实测 N=44）
- 测试数据：user_id=1, product_id=1, quantity=44
- 操作步骤：调用 POST /orders，body = `{"user_id":1,"product_id":1,"quantity":44}`
- 预期结果：状态码 201；商品1库存变为 0
- 实际结果：201；order_id=8；quantity=44；total_price=8756.0（=199×44，金额正确）；执行后键盘库存为 0
- 执行状态：通过

### TC-ORDER-003 数量 = 库存+1（越界·非法）
- 测试模块：订单创建
- 测试目的：验证数量超过库存时被拒绝，且不产生订单、不扣库存
- 前置条件：用户 id=1；商品 id=1 当前库存 = N
- 测试数据：user_id=1, product_id=1, quantity=N+1（实测传入 45）
- 操作步骤：调用 POST /orders，body = `{"user_id":1,"product_id":1,"quantity":45}`
- 预期结果：状态码 409，detail="库存不足"；商品1库存不变
- 实际结果：409，detail="库存不足"
- 执行状态：通过
- 执行备注：本次实际执行顺序为先 002 后 003，执行 003 时库存已为 0，409 的成因是"库存为 0"而非"刚好超出边界 1"，边界验证精度弱化。如需严格验证，应先执行 003 再执行 002。教训：**用例执行顺序会影响验证强度**。

## 四、设计方法自查清单（学生作业场景）

1. 商品不存在（product_id 传一个不存在的值）
2. 用户不存在（user_id 传一个不存在的值）
3. 数量为 0（非法输入）
4. 数量为负数（非法输入）
5. 数量为非整数或非数字（非法输入）
6. 数据一致性（下单成功后，核对：库存精确减少、订单金额 = 单价 × 数量）
7. 重复请求（同样的下单请求连续发两次，观察并说明：是否产生两张订单？库存扣几次？这算 bug 吗？）

## 五、用例 TC-ORDER-004 ~ 010（已执行 9 条）

### TC-ORDER-004 商品不存在（等价类 · 非法）
- 测试模块：订单创建
- 测试目的：验证商品 id 不存在时下单被拒绝，且不产生订单
- 前置条件：用户 id=1 存在
- 测试数据：user_id=1, product_id=999（不存在）, quantity=1
- 操作步骤：POST /orders，body = `{"user_id":1,"product_id":999,"quantity":1}`
- 预期结果：状态码 404，detail="商品不存在"；orders 表无新增；库存不变
- 实际结果：404，detail="商品不存在"
- 执行状态：通过
- 设计理由：product_id 是输入，等价类 = {存在, 不存在}，取"不存在"作代表值。

### TC-ORDER-005 用户不存在（等价类 · 非法）
- 测试模块：订单创建
- 测试目的：验证用户 id 不存在时下单被拒绝
- 前置条件：商品 id=1 存在
- 测试数据：user_id=999（不存在）, product_id=1, quantity=1
- 操作步骤：POST /orders，body = `{"user_id":999,"product_id":1,"quantity":1}`
- 预期结果：状态码 404，detail="用户不存在"；无订单；库存不变
- 实际结果：404，detail="用户不存在"
- 执行状态：通过
- 设计理由：代码里先查用户再查商品，校验有先后，所以"用户不存在"和"商品不存在"是两条不同用例，不能合并。

### TC-ORDER-006 数量为 0（边界值下边界 · 非法）
- 测试模块：订单创建
- 测试目的：验证数量为 0 被校验拦截
- 前置条件：用户 id=1、商品 id=1 存在
- 测试数据：user_id=1, product_id=1, quantity=0
- 操作步骤：POST /orders，body = `{"user_id":1,"product_id":1,"quantity":0}`
- 预期结果：状态码 422（不是 400/409）；无订单；库存不变
- 实际结果：422；type=greater_than；loc=[body, quantity]；msg="Input should be greater than 0"；input=0
- 执行状态：通过
- 设计理由：0 是"合法区间(1~N)"下边界之外一格，属边界值三件套之一。422 由 `Field(gt=0)` 在请求校验层拦截，不会进入业务逻辑。

### TC-ORDER-007 数量为负数（等价类 · 非法）
- 测试模块：订单创建
- 测试目的：验证数量为负被校验拦截
- 前置条件：用户 id=1、商品 id=1 存在
- 测试数据：user_id=1, product_id=1, quantity=-1
- 操作步骤：POST /orders，body = `{"user_id":1,"product_id":1,"quantity":-1}`
- 预期结果：状态码 422；无订单；库存不变
- 实际结果：422；type=greater_than；msg="Input should be greater than 0"；input=-1
- 执行状态：通过
- 设计理由：-1 与 0 同属"≤0"等价类，但边界值通常把 0 单列，负数单独测一次即可。

### TC-ORDER-008 数量为非整数（等价类 · 非法类型）
- 测试模块：订单创建
- 测试目的：验证数量传小数/字符串等非法类型被校验拦截
- 前置条件：用户 id=1、商品 id=1 存在
- 测试数据：user_id=1, product_id=1, quantity=2.5（或 "abc"）
- 操作步骤：POST /orders，body = `{"user_id":1,"product_id":1,"quantity":2.5}`
- 预期结果：状态码 422；无订单；库存不变
- 实际结果：422；type=int_from_float；msg="Input should be a valid integer, got a number with a fractional part"；input=2.5
- 执行状态：通过
- 设计理由：类型错误与取值范围错误是两种 422，但都属于"非法类型"等价类，取 2.5 一个代表即可。

### TC-ORDER-009 数据一致性（核心用例，待执行）
- 测试模块：订单创建
- 测试目的：验证下单成功后，库存精确减少、订单金额正确、订单记录正确落库
- 前置条件：用户 id=1；商品当前库存 = N；记录下单前库存 stock_before = N
- 测试数据：user_id=1, product_id=2（无线鼠标，库存充足）, quantity=Q（1 ≤ Q ≤ N）
- 操作步骤：
  1. GET /products 记录商品库存 stock_before
  2. POST /orders，记下返回的 order_id 和 total_price
  3. GET /products 记录商品库存 stock_after
  4. 用 SQL 查 orders 表该 order_id 的 total_price、quantity、status（阶段 6 补做）
- 预期结果：状态码 201；stock_after == stock_before − Q；返回的 total_price == 单价 × Q；数据库里 status == "created"
- 实际结果：201；order_id=9；product_name=无线鼠标；quantity=2；total_price=178.0（=89×2，金额正确）；status=created。执行说明：因键盘库存被 002 清零，本条按计划改用商品2无线鼠标执行（等价数据替代）
- 执行状态：通过
- 设计理由：**只断言 HTTP 返回 201 不足以证明业务正确**——接口可能"假装成功"但没扣库存、或金额算错。所以必须追加数据库断言。这条是阶段 6"数据库校验"的雏形，也是面试必考。

### TC-ORDER-010 重复请求（状态迁移 · 观察题）
- 测试模块：订单创建
- 测试目的：观察同样的下单请求连续发两次会发生什么，并判断是否为缺陷
- 前置条件：用户 id=1、商品 id=1 库存充足
- 测试数据：两次完全相同的 body = `{"user_id":1,"product_id":1,"quantity":1}`
- 操作步骤：把同一请求连续 Execute 两次；记录两次的状态码和返回；GET /products 看库存
- 预期结果（当前系统的实际行为）：两次都返回 201，产生**两张**订单，库存**扣了两次**
- 实际结果：两次均 201（order_id=6、order_id=7），生成两张独立订单，库存共扣减 2；当前系统未实现幂等，属已知行为
- 执行状态：通过
- 设计理由：当前系统**没有做幂等**（幂等 = 同一请求重复发，效果只发生一次）。是否算 bug 取决于业务需求是否要求幂等。**先回答"为什么这样"，再回答"你觉得要不要改成幂等"。**

## 六、执行小结

- 共 10 条用例：**10 条全部通过**（2026-10-18，Apifox 手工执行）。
- 重要教训 1：占位符（如 N）必须替换为真实值，JSON 中不能出现字面量字母，否则触发 422 json_invalid（与字段校验的 422 是两种不同错误）。
- 重要教训 2：Apifox 的"通过/失败"标签只看状态码是否为 2xx；**用例是否通过取决于"实际结果是否符合预期结果"**，404/409/422 用例同样可以是通过。
- 重要教训 3：用例之间有数据依赖（002 清零库存影响 003 的边界精度），执行顺序是测试设计的一部分。
